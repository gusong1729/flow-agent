## 一、DeepSeek：账号登录到底是怎么"自动给 token"的

### 实际机制

不是"登录 → 发一个 API Key"，而是**OAuth 授权码 + PKCE**，回调落在本机：

1. 应用在本机 webServer 上临时注册 `/oauth/callback` 路由。
2. 拉起浏览器到 DeepSeek Platform 授权页，带 PKCE challenge、客户端版本、当前语言、UTC 偏移。
3. 用户登录授权后，浏览器回调本机，应用用 PKCE verifier 换 token。
4. 拿到的 token 用于模型请求时放在 **`x-dsh-auth-token`** 请求头（注意：**不带 `Bearer` 前缀**，跟 API Key 的认证方式完全不同）。
5. 本地取消有决定权：取消会作废远程申请和未兑换的 code；迟到的兑换结果直接丢弃。
6. 退登 = 先删本地授权，再调 `POST /auth-api/v0/users/logout`；远端失败不回滚登录态。
7. 首次请求失败后最多重试 5 次，指数退避默认从 1 秒起。

### 三个关键限制（决定了它能不能被第三方复用）

| 限制 | 含义 |
|---|---|
| **token 只对配置的 `inferenceOrigin` 有效**（默认 `https://api.deepseek.com`） | 改了请求地址不会让账号凭证跟着转发；请求拒绝重定向 |
| **每次调用携带 5 个 Platform 客户端身份请求头**，由发起界面的版本、语言、UTC 偏移推导 | 身份属于"发起调用的界面"，不是服务器。第三方应用伪造这组头 = 逆向 |
| **文档明确写了「API Key 与账号记录独立保存」**，并把「把 token 塞进 `DEEPSEEK_API_KEY`」列为被否决的方案 | 账号登录 ≠ 拿到 API Key，这是刻意的设计区分 |

### 对你自建应用的含义

「用户登录 DeepSeek，我的 App 就能调模型」有三条路，成本与合规性差别很大：

| 路线 | 做法 | 代价 |
|---|---|---|
| A. 用户自带 API Key | 设置页让用户填 `sk-…`，存本地 | 最稳、零风险；但"登录即用"的体验没了 |
| B. 服务端持 Key | 用户登录**你的**账号体系，你的后端持 Key 转发 | 这才是市面上"登录就能用"的通用实现；要自己做限额/计费，且你的 Key 一旦泄漏是你赔 |
| C. 复刻 DSH 的 OAuth | 逆向客户端身份 + PKCE + 本地回调 | 脆弱（平台改头就挂）、且属于未经授权使用，不建议 |

**结论：C 不要做。** 如果你的目标是"用户不填 Key 就能用"，正解是 B——但那已经是"做服务"而不是"做工具"了。个人项目阶段建议先 A。

> 补：确实存在第三方复刻设备码流程的项目（如 `molly-ovo/dsh-workbuddy-oauth`，把 WorkBuddy 的模型接进 DSH），但那是把**别家服务**的授权接进 DSH，不是 DeepSeek 开放了给第三方的 OAuth。我在公开文档里**没有找到** DeepSeek 面向第三方应用的 OAuth 应用注册说明——这一点是"未确认"，若要做需要另行核实。

## 二、MiniMax：两套 Key、两个兼容面

### 两套 Key（互不通用）

| 类型 | 位置 | 用途 |
|---|---|---|
| 按量付费 API Key | 接口密钥 → 创建新 API Key | 按 token 计费 |
| **M Plan 订阅 Key** | 订阅管理 → M Plan（`/user-center/payment/token-plan`） | 订阅套餐与已购积分，**与按量 Key 相互独立** |

你说的 "token plan" 就是后者：M Plan 的订阅 Key。

### 两个兼容面（这点很关键）

| 兼容面 | baseURL | 说明 |
|---|---|---|
| OpenAI 兼容 | `https://api.minimax.cn/v1` | 走 OpenAI SDK |
| **Anthropic 兼容（官方推荐）** | `https://api.minimax.cn/anthropic/v1` | 走 Anthropic SDK，能拿到 `reasoningText` |

模型：`MiniMax-M3.1-Flash`、`MiniMax-M3`，均标称 1,000,000 上下文、原生多模态。另有官方 AI SDK provider：`@minimax-ai/ai-sdk-provider`。

> 注意：MiniMax 同时提供 OpenAI 面与 Anthropic 面，意味着你的供应商抽象层**不能只按 OpenAI 一种协议建模**。这是下面第三节的直接输入。

来源：[MiniMax 平台文档（接口概览）](https://platform.minimax.cn/docs/llms-full.txt)

## 三、自定义供应商：hanako（`liliMozi/openhanako`）是怎么做的

它开源、支持自定义模型，是"多供应商 + 自定义"的一个可参考真实实现。我读了它的配置样例和 provider 层源码。

### 三层结构

| 层 | 文件 | 职责 |
|---|---|---|
| **目录层** | `core/provider-catalog.ts` → `provider-catalog.json`（v2） | 供应商注册表：providers map + capabilities + `_deleted_providers`（记录被删的，防止同步时复活）；从旧的 `added-models.yaml` 迁移而来 |
| **兼容层** | `core/provider-compat.ts` + `provider-compat/<vendor>.ts` | 每个供应商一个模块，导出 `matches(model)` 与 `apply(payload, model, options)`；dispatcher 按数组顺序 **first-match-wins** |
| **同步层** | `core/model-sync.ts` + `shared/model-capabilities.ts` | 从供应商拉模型列表，并投影出每个模型的 `compat.thinkingFormat` / `compat.reasoningProfile` 等能力位 |

它的兼容层纪律写得很硬，直接抄得动：

- 所有出站 payload 兼容**只有一个入口** `normalizeProviderPayload()`，chat 路径和 utility 路径共用。
- 与供应商无关的通用补丁（空 tools 剥离、孤儿 toolResult 配对兜底、reasoning replay）留在主入口，不散落到调用点。
- 供应商专属补丁必须拆独立文件，文件头 JSDoc 要写清「处理哪个供应商 / 解决什么协议问题 / **什么条件下整个文件可以删掉**」。
- 新增供应商默认加在数组**末尾**；只有当它的 `matches` 是另一个模块的子集（更具体）时才前置，否则会被通用规则吞掉。
- 必须容忍 `model = null`，`matches` 不得抛错。

### 它自己写的一句话，值得贴墙

> **`OpenAI-compatible` 只说明请求大信封相似，不说明 thinking 控制、tool replay、effort 枚举等细节兼容。**

这句话决定了你的供应商设计：**"填个 baseURL 就完事"能跑通简单对话，但一定会在这几处翻车**——`thinking` / `reasoning_effort` 字段名不一致、`max_tokens` 被 SDK 隐式塞上限、历史里的 `reasoning_content` 要不要回放、空 tools 数组某些厂商会报错。

### 给我们的最小可行抽象

不抄它三层，抄它的**边界**：

```
Provider = { id, label, protocol: "openai" | "anthropic", baseURL, apiKey, models[] }
Model    = { id, contextWindow?, quirks?: { thinkingField?, dropEmptyTools?, ... } }
```

- 协议只有两种（OpenAI / Anthropic），覆盖 DeepSeek、MiniMax、hanako 这类自定义站绝大多数情况。
- 供应商差异用 `quirks` 声明式表达，**不写代码分支**，等真的撞墙再升级成 compat 模块。
- Key 存本地文件（`0600`），不写进配置仓库。

来源：
- [hanako 配置样例](https://github.com/liliMozi/openhanako/blob/main/lib/config.example.yaml)
- `core/provider-compat/README.md`、`core/provider-catalog.ts`（同上仓库）

## 四、界面方向：本地已有设计技能

`skills/kz-design/`（K叔Design v1.0.9）就是这个场景该用的技能，覆盖高保真 HTML 原型、设计方向探索、配色/布局/形态密度、反 AI slop、验证闭环、实现交接。**注意它不在 `.agents/skills`，技能目录里看不到，要按路径读。**

### 直接可用的硬约束（摘自其 `references/design-quality-rules.md`）

反 AI slop 默认避免：
- 紫蓝渐变、赛博霓虹、深蓝科技底当"高级感"
- 装饰性 emoji、每标题配 icon、无意义状态点
- 圆角卡片叠卡片、左色条 accent、无依据的玻璃拟态
- 全场用 Inter / Roboto / system font 做 display，没有排版个性

视觉硬约束：
- UI 卡片不套进页面卡片；重复列表项可以是卡片，页面区块不要都做成漂浮卡
- 固定格式元素要有稳定尺寸，不被 hover 或动态文本撑变形
- 字号不随 viewport 无限缩放
- 配色不能读成单一色相堆叠

动手前必须先写一句 **aesthetic thesis**（服务谁、什么语气、哪个细节最该被记住、复杂度边界），且**每个产物只保留 1 个主记忆点**。

### 本产品的 aesthetic thesis 草案

> 服务「白天在餐厅现场跑点位、晚上回点位汇总」的项目统筹，语气是**工作台**而不是聊天玩具：克制、密度高、一眼能找到今天还有哪些轮次没交。主记忆点是**左对话 / 右画布的静态分栏**——文字说完，图就在旁边长出来，不需要切换页面。复杂度边界：不做花哨动效，不做卡片套卡片。

## 五、还没定的

1. **形态与运行位置**：桌面 / PWA / 本地服务，决定了 OAuth 回调和 Key 存在哪。
2. **用户是谁**：只有你自己用（Key 存本地，走 A），还是要给别人用（得上 B）。
3. **首版协议**：先只做 OpenAI 兼容一种，还是一次做两种协议。
