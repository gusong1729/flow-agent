# datacollect-flow：采集规则 → 现场能执行的任务单

基于 [workflow-visualizer](https://github.com/jimku233/workflow-visualizer)（MIT，见 `NOTICE.md`）改造成数采项目统筹专用。

渲染器：`scripts/flow.mjs`（相对本 skill 目录）。字段语法手册：`references/spec.md`（**写规格前必读**）。

## 零、这份技能服务的是什么

数采项目统筹的交付物不是"一张图"，是**采集员拿着就能干、客户看了能批、出了问题能查**的东西。图只是载体；图里每个节点都必须对应一个现场真实发生的动作、一台真实存在的设备、一个具体的人。

所以本技能的第一原则：**图上每句话都要能在现场落地**。写不出来的地方是没核实，不是可以含糊过去——标 `status: hold` 并在 `note` 写清待确认什么。

## 一、四类产物，先选对

| 产物 | 给谁看 | 模板 |
|---|---|---|
| **拍摄任务单** | 组长 / 审批 / 客户 | `examples/任务单-餐饮摆台.json` |
| **早会执行卡** | 采集员（手机，竖着拿） | `examples/早会执行卡-竖版.json` |
| **设备异常决策树** | 现场 / 远程支持 / 技术 | `examples/异常决策树-设备.json` |
| **返工复盘** | 自己 / 客户 | 拿任务单模板改 `status` 和 `note`，不另建 |

一次 `render` 会在**同一个 HTML 里同时出横版和竖版**：横版长流程自动分栏、电脑一屏看完；竖版单列、手机竖向滚动。页面按窗口比例自动选，底部可手动切。所以**不需要为手机另做一份**，只要保证竖版读起来也通顺。

> ⚠️ **不要为了"横向"去写 `direction: "LR"`。** 上游实现里 `LR` 是先按纵向排好再整体转置，节点宽高会互换，长链会得到一条极扁的长条、缩完字很小。要横向就用默认的 `TD` 让它自动分栏（必要时 `--wrap N` 指定每栏行数）。`LR` 只在画**宽而浅的树**（比如异常决策树那种一分支到底的结构）时才用。

## 二、第一步：从客户规则里提五要素（这步不能省，也不能交给模型）

固定抓这五样，缺一条就停下来问：

1. **场景**：在哪里拍（餐饮/酒店/商超的哪个具体区域、什么台面、多大空间）
2. **物品**：用哪些具体东西（名称、数量、是否现场可得、是否允许替代品）
3. **动作顺序**：手怎么拿、怎么移、怎么放，双手如何配合，一轮做几步，做几轮
4. **拍摄要求**：用什么设备组合、镜头朝哪、哪些部位必须在画面内、哪些遮挡算废片
5. **合格判定**：什么样才算合格（时长、完整度、遮挡、光线、动作是否出画）

**AI 该做和不该做的分界**（对应岗位职责第 1 条）：

- ✅ 可以交给模型：批量构思候选场景与动作步骤、把规则改写成采集员能读懂的短句、检查动作描述是否自相矛盾。
- ❌ 不能交给模型：场地时间能不能约到、物品现场有没有、设备够不够、采集员会不会做。**这四件必须你去核实**，核实结果写进 `detail`，核实不了就写 `status: hold` + `note` 说明卡在哪。

## 三、第二步：写规格

### 选 JSON 还是 Mermaid

- 只有线性顺序、没有时间/负责人/拍摄要求 → 写 `.mmd`（Mermaid），最省事。
- 要带人、时间、合格标准、阶段分组 → **写 JSON**。任务单几乎总是这种，因为信息密度必须够。

### 字段怎么映射到数采语境

| 字段 | 在这里写什么 | 反例（别这么写） |
|---|---|---|
| `label` | 一个动作，动词开头 | "摆台流程"（那是标题不是动作） |
| `time` | **目标用时**，如 `目标 40s` | "9:00–9:40"（那是排期不是任务单） |
| `owner` | 谁做：采集员/组长/场地/技术 | "团队"（没人会对号入座） |
| `detail` | 拍摄要求 + **合格判定** | "按要求拍摄"（等于没写） |
| `note` | **红线**，做错整条作废的那种 | "注意安全"（红线不红就不是红线） |
| `status` | 现场真会变的状态 | 给每个节点都标 `done`（那是装饰） |
| `groups` | 阶段带：进场准备 / 试拍确认 / 正式采集 / 校验上传 | 按人分组（按人分应写在 `owner`） |
| `kind: decision` | 真判断，必须两条出边且都带标签 | "是否继续"（没有具体判据） |

### 起手最快的方式

```powershell
node "scripts\flow.mjs" sample --out ".\out\我的任务单.json"
```

拿到的是一份能跑的完整规格，改 `nodes` 和 `edges` 就行。**不要从空文件开始写。**

## 四、第三步：校验 + 渲染

```powershell
$sk = "scripts\flow.mjs"
node $sk check  ".\out\我的任务单.json"
node $sk render ".\out\我的任务单.json" --all --out ".\out\我的任务单.html"
```

### `check` 查出的四个问题，在任务单语境里各是什么意思

这一步是本技能最值钱的地方——它不是代码检查，是**任务单体检**：

| 报错 | 字面意思 | 在任务单里意味着 |
|---|---|---|
| 孤立节点 | 没有任何连线 | 这一步**没写谁触发、做完了交给谁** |
| 不可达 | 从起点走不到 | 缺前置条件，**现场根本执行不到** |
| 无终点 | 没有任何出口 | **没有验收环节**，数据交不出去 |
| 成环 | 能绕回自己 | **返工死循环**：条件不满足就永远卡在这一步 |

**出口码**：`0` 通过；`1` 是 `check` 发现结构问题；`2` 是参数或输入写错。看到 `1` 不要忽略就渲染，"不可达"在现场意味着那条流程永远走不到。

## 五、写任务单的红线

1. **一个节点一个动作**。把"佩戴设备、开机、试拍"塞进一个节点，采集员到现场会漏做中间那步。
2. **判断节点必须有判据**。`label` 写"画面是否被小臂遮挡"，不要写"是否需要调整"——后者采集员会自己给自己判通过。
3. **合格标准进 `detail`，红线进 `note`**。反过来写会让现场分不清"建议"和"废片"。
4. **时间写目标用时，不写钟点**。任务单是发给一个人做一件事的；排期是另一张表。
5. **别为了图好看加节点**。图上多一个装饰节点，现场就多一次误判。
6. **不确定的标 `hold`**。`status: hold` + `note: "待确认：场地是否允许使用陶瓷餐具"` 比编一个答案安全得多。

## 六、渲染出来的东西能拿去干什么

- **双击 HTML**：离线可用，不联网、无 CDN。点任意节点看时间/负责人/说明，`Ctrl+F` 或页面搜索框搜环节名、负责人、说明。
- **导 SVG / PNG**：`--all` 已一并产出，拖进 PPT 或钉钉/企微通知里。
- **复制 Mermaid 源码**：粘进飞书文档、语雀、GitHub issue、Typora，对方能改能版本化。
- **手机看**：电脑上起服务，同一 Wi-Fi 下手机打开（采集员站在现场用手机比打印纸条实际）：

```powershell
node "scripts\serve.mjs" ".\out" 8765
```

产物是**自包含快照，不会自动更新**。改了规格要重新 `render`（或 `refresh` 整个目录）。页面右下角写着生成器版本；首页会把旧版渲染的文件标出来。

## 七、边界：它不管什么

写清楚，免得硬塞：

| 需求 | 该用什么 | 为什么不用流程图 |
|---|---|---|
| 数十人排班、点位时段分配 | Excel / 多维表格 | 是二维资源匹配，不是流程 |
| 每日产量汇总（设备数/时长/上传/合格时长） | Excel / 多维表格 | 是数据表，图上一格都放不下 |
| 客户沟通记录、催办台账 | 多维表格 / 待办工具 | 是状态机台账，不是作业流程 |
| 设备台账、库存 | 表格 | 同上 |

但**图和数据要对得上**。建议汇总表就用下面这套表头，图里的任务编号直接当外键：

```csv
日期,点位,任务编号,任务名称,采集员,设备编号,设备类型,计划轮次,完成轮次,拍摄时长(分),上传状态,合格时长(分),异常类型,异常说明,处理人,是否补拍
```

`异常类型` 建议固定枚举，和决策树的五个分支一一对应：`连接不上 / 无法录制 / 录制中断 / 文件找不到 / 上传失败`。这样复盘时能直接按分支统计，看出哪类问题最耗人。

## 八、常见报错

| 现象 | 原因 | 处理 |
|---|---|---|
| `flow: 文件:行:列: ...` | JSON 语法错 | 按行列号改，通常是缺逗号或尾逗号 |
| 中文乱码 | 文件不是 UTF-8 | 另存为 UTF-8（无 BOM） |
| 横版一栏挤成一长条 | 节点太多没分栏 | 加 `--wrap 6` 指定每栏行数，或先 `--debug` 看分栏结果 |
| 菱形里的字被挤断 | `label` 太长 | 判断节点的 `label` 压到 12 字内，细节挪进 `detail` |
