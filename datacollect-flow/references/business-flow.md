# 数采业务全流程 · 画图时照这个写

> 依据：内部《数采业务全流程架构文档》V1.0（2026-08-29）+《具身智能数采项目统筹（AI 任务设计方向）》岗位说明。
> 本文只做一件事：**把业务事实翻译成流程图的字段**。业务口径以那两份为准，本文不改写它。

## 一、先记住三个词

| 词 | 含义 | 为什么它决定图怎么画 |
|---|---|---|
| **需求标准** | 甲方要什么场景/动作/数量/质量、什么时候交 | 每个采集类节点的 `detail` 必须能追溯到某条需求，否则这个节点站不住 |
| **有效时长** | 通过质检、满足甲方要求的时长，**只有它参与结算** | 图上必须有"质检→有效时长"这一段，不能只画"采完了"就结束 |
| **过程记录** | 谁、在哪、用什么设备、采了多少、有什么问题 | 台账与异常在图上要成节点，不能只写在一句话里 |

一句话：**业务本质是把真实场景变成合格数据，再变成客户认可的交付成果。** 图要能让人看到"哪一步决定了数据合不合格"。

## 二、七环节主干（所有图都挂在这条骨架上）

| # | 阶段 | 要解决什么 | 主要动作 | 关键产出 |
|---|---|---|---|---|
| 1 | 需求与订单 | 要采什么、采多少、什么时候交 | 需求确认 → 报价签约 → 试采验证 | 订单、验收标准、结算口径 |
| 2 | 采集准备 | 能不能采、谁来采、用什么采、怎么采 | 场景确认 → 人员培训 → 设备准备 → 排期 | 培训记录、设备清单、采集排期 |
| 3 | 现场采集 | 按标准把数据采回来 | 按标准执行 → 过程记录 → 异常上报 → 达成当日目标 | 原始数据、采集记录 |
| 4 | 上传与台账 | 数据是否完整、可追溯 | 当天上传 → 登记台账 → 完整性检查 | 上传记录、采集台账 |
| 5 | 质检与筛选 | 数据是否达标 | 按甲方要求筛选 → 剔除无效 → **统计有效时长** → 核对台账 | 合格数据、有效时长统计、差异分析 |
| 6 | 交付与结算 | 客户是否验收、费用如何结算 | 按约定交付 → 确认验收 → 按口径对账 → 结算留底 | 交付记录、验收确认、结算明细 |
| 7 | 复盘与迭代 | 下次如何做得更好 | 对比计划与有效时长 → 分析差异 → 更新流程/培训/设备 → 沉淀标准 | 改进清单、更新后的标准 |

**流程特点**（文档原文）：环环相扣、质量是核心、可追溯、持续迭代。

## 三、字段怎么对上

| 规格字段 | 在这个业务里写什么 | 反例 |
|---|---|---|
| `groups` | **就用上面七个阶段名**（带序号），不要自创分法 | "上午/下午"——那是排班不是流程 |
| `label` | 一个动作，动词开头 | "采集准备"（那是阶段名，放 `groups`） |
| `owner` | 甲方 / 项目统筹 / 采集员 / 组长 / 技术 / 质检 | "团队" |
| `time` | **目标用时**或**时限**（"当天""次日 10:00 前"） | 钟点区间（那是排期表） |
| `detail` | 动作标准 + **合格判定**（可追溯到需求） | "按要求采集" |
| `note` | 红线：做错整条作废 / 影响结算 | "注意安全" |
| `status` | `todo` 待做 / `doing` 进行中 / `done` 已完成 / `hold` 阻塞待确认 / `risk` 需人工把关 | 全部标 `done` |
| `kind: decision` | 真判断，两条出边带标签 | "是否继续" |
| `kind: milestone` | 验收点：试采验收 / 质检合格 / 客户验收 | 随便用 |

## 四、四类产物，各自从哪儿切

| 产物 | 从骨架的哪一段切 | 给谁看 | 默认文件名 |
|---|---|---|---|
| **业务全流程总览** | 完整七环节 | 自己 / 新人 / 客户沟通 | `业务全流程-七环节.json` |
| **拍摄任务单** | 第 3 环内部（现场采集）展开到动作级 | 组长 / 审批 / 采集员 | `任务单-<场景>.json` |
| **采集准备清单** | 第 2 环展开 | 自己 / 组长 | `采集准备-<点位>.json` |
| **异常处置决策树** | 第 3–4 环的异常分支 | 现场 / 技术 | `异常决策树-设备.json` |

判据：**总览图讲"业务怎么走"，任务单讲"这一轮怎么拍"，决策树讲"出问题找谁"。** 三者不要混在一张图上。

## 五、写图时必须成立的四条

1. **每个采集类节点都要能指回一条需求**（否则是拍脑袋加的步骤）。
2. **必须有质检段**，且明确"剔除无效 → 统计有效时长"。没有这一段，图上就等于承认"采了就算钱"，与业务事实不符。
3. **异常必须有出口**：设备/场地/人员/数据异常，至少各有一条路径到"上报 → 处置 → 恢复或改期"。
4. **台账与上传是节点，不是备注**：漏了它们，晚上汇总时就没有可核对的东西。

## 六、口径纪律（重要）

- 文档里的**单价、时长、订单规模都是示例，不代表当前合同口径**。图上要出现数字，必须标来源或写"待确认"。
- 涉及甲方标准但尚未拿到的，`status: hold` + `note: "待确认：<具体缺什么>"`，**不要编一个看起来合理的数**。
- 设备/场景由谁提供（甲方提供 vs 自建执行）会改变 `owner` 与结算单价，图上要显式区分，别混着画。

## 七、术语（图上直接用这些词）

甲方 / 数采 / 试采 / 长期订单 / 场景 / 原始数据 / 有效数据 / **有效时长** / 质检 / 结算单价 / 台账。
新人看不懂的词不要上图——先换成上面的说法，或者写进该节点的 `detail`。
